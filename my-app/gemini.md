# 프로젝트 개발 가이드

이 문서는 재봉 공장 ERP 프로그램 개발을 위한 기준과 합의된 사항을 정리합니다. 프로젝트 참여자는 이 문서를 기준으로 개발을 진행합니다.

## 1. 프로젝트 개요

- **프로젝트명**: 재봉 공장 ERP 시스템
- **목표**: 재봉 공장의 생산, 인사, 재고 등 전반적인 업무를 관리하는 ERP 프로그램을 개발합니다.
- **주요 소통 언어**: 한국어

## 2. 기술 스택 (Tech Stack)

- **주요 언어**: TypeScript
- **프레임워크**: React (Vite 기반)
- **UI 라이브러리**: MUI (Material-UI)
- **라우팅**: React Router
- **스타일링**: Emotion (`sx` prop) / MUI

## 3. 프로젝트 구조

- `src/`: 소스 코드 루트 디렉토리입니다.
- `src/pages/`: 각 페이지(화면)에 해당하는 컴포넌트를 위치시킵니다. (예: `Login.jsx`, `Factory.jsx`)
- `src/components/`: 여러 페이지에서 재사용되는 공통 컴포넌트를 위치시킵니다.
- `src/layouts/`: 페이지의 전체적인 Layout을 정의하는 컴포넌트를 위치시킵니다.
- `src/context/`: 전역 상태 관리를 위한 React Context를 위치시킵니다.
- `src/theme/`: MUI 테마 커스터마이징 관련 코드를 위치시킵니다.
- `src/router.jsx`: 애플리케이션의 라우팅 설정을 정의합니다.

## 4. 개발 컨벤션 및 규칙

*이 섹션은 프로젝트 진행에 따라 지속적으로 업데이트됩니다.*

### 4.1. UI 개발 및 스타일링
- **UI 라이브러리**: 모든 UI 컴포넌트는 MUI를 우선적으로 사용하여 구현합니다.
- **스타일링 및 우선순위**:
  1. **전역 스타일**: `src/styles/` 내의 CSS 파일들은 `src/index.jsx`에서 최상단에 임포트하여 애플리케이션 전체의 기본 스타일을 설정합니다.
  2. **개별 스타일**: 각 페이지나 컴포넌트에만 적용되는 스타일은 해당 파일 내에서 임포트하거나 정의합니다.
  3. **우선순위**: `전역 CSS` < `개별 페이지/컴포넌트 CSS` < `MUI sx prop` 순서로 적용되어, 개별 설정이 전역 설정을 덮어쓰도록 합니다.
  4. **권장 사항**: 컴포넌트 단위의 스타일링은 `sx` prop 사용을 권장합니다. 복잡한 스타일은 별도 CSS로 분리할 수 있습니다.
- **컨테이너 스타일**: 콘텐츠를 감싸는 컨테이너(예: `Paper`)는 그림자(`elevation`) 사용을 지양하고, 대신 외곽선(`variant="outlined"`)을 사용하여 평평하고 인더스트리얼한 디자인 통일성을 유지합니다. 이는 애플리케이션에 보다 깔끔하고 전문적인 느낌을 부여합니다.

  **적용 예시:**
  ```jsx
  // 지양 (Avoid)
  <Paper elevation={3} sx={{ p: 2 }}>
    ...콘텐츠...
  </Paper>

  // 권장 (Recommended)
  <Paper variant="outlined" sx={{ p: 2 }}>
    ...콘텐츠...
  </Paper>
  ```

### 4.2. 상태 관리
- 간단한 상태는 컴포넌트 내부의 `useState`를 사용하고, 여러 컴포넌트에 걸쳐 사용되는 전역 상태는 `Context API`를 활용합니다.

### 4.3. 파일 및 컴포넌트 명명
- 컴포넌트 파일명은 `PascalCase`를 따릅니다. (예: `MyComponent.jsx`)
- 일반적인 함수나 변수는 `camelCase`를 따릅니다.

### 4.4. API 연동
- API 요청 및 데이터 처리에 대한 규칙은 추후 정의합니다.

### 4.5. 코드 스타일
- 프로젝트에 설정된 Prettier와 ESLint 규칙을 따릅니다. (설정 필요)

### 4.6. 전역 스타일 관리
애플리케이션의 전역 CSS 스타일은 `src/styles/` 디렉토리 내에서 기능별로 분리된 파일들로 관리됩니다. 이 파일들은 `src/index.jsx`에서 임포트되어 전역적으로 적용됩니다.

- **`base.css`**: 애플리케이션 전반의 기본 스타일을 정의합니다. (예: `body`, `html` 태그 스타일, 기본 폰트 설정 등)
- **`theme.css`**: 색상, 폰트 크기, 그림자 등 디자인 시스템의 테마와 관련된 변수나 클래스를 정의합니다.
- **`layout.css`**: 주요 레이아웃 구조(예: 헤더, 사이드바, 컨텐츠 영역)와 관련된 스타일을 정의합니다.
- **`table.css`**: 테이블 컴포넌트의 공통 스타일을 정의합니다.
- **`form.css`**: 입력 필드, 버튼 등 폼(Form) 요소들의 공통 스타일을 정의합니다.

## 6. 프론트엔드 구조 규칙 (Frontend Architecture Rules)

일관성 있는 개발을 위해 다음 구조 규칙을 모든 도메인에 적용합니다.

### 6.1. Board / Detail 화면 구조 규칙

- 각 도메인의 라우팅 진입점은 `{domain}.jsx` 파일이다.
- 진입점 이후 최초로 렌더링되는 화면은 항상 Board이다.
- Board는 해당 도메인의 업무 허브 역할을 하며, 리스트(List), 검색, 필터, 요약 정보 등을 포함할 수 있다.
- Board는 단일 객체를 생성하거나 저장하지 않으며, Detail 화면으로의 진입만 담당한다.

- Detail은 Board의 하위 개념이다.
- Detail은 단일 객체의 생성/수정/상세 설정을 담당하는 작업 세션 단위 화면이다.
- Detail은 항상 Board를 통해 진입한다.

- Detail의 실제 UI는 `detail/` 하위 컴포넌트로 분리한다.
- Detail 진입점은 상태 관리 및 저장 로직을 총괄하며, 하위 컨텐츠는 UI와 입력만 담당한다.

**폴더 및 파일 구조 예시**

- `style.jsx` : Style 도메인 라우팅 진입점
- `style/styleboard.jsx` : Style 도메인의 Board 화면
- `style/styledetail.jsx` : Style 도메인의 Detail 진입점
- `style/detail/styleinfo.jsx` : Detail 하위 컨텐츠(탭 단위)

### 6.2. 기타 구조 규칙
1.  **라우트와 화면의 분리**: `src/pages`는 라우팅 진입점 전용입니다. 실제 UI와 로직을 담은 화면(예: `StyleBoard.jsx`, `StyleDetail.jsx`)은 `src/pages/App/{도메인명}/` 폴더에서 관리합니다.

2.  **Board / Detail 패턴**: 모든 도메인은 Board와 Detail 화면으로 구성됩니다.
    -   **`Board`**: 목록 표시, 검색, `Detail` 화면으로 네비게이션 역할만 수행합니다.
    -   **`Detail`**: 단일 데이터의 생성/수정 세션을 관리하며, 하위 탭들의 저장 로직을 총괄합니다.
    -   `Board`와 `Detail`은 ID로만 데이터를 주고받으며, 상태를 직접 공유하지 않습니다.

3.  **페이지 레이아웃 (Page Layout)**:
    -   **제목 및 구분선 제거**: 상위 탭(Tab) UI에서 페이지 제목을 표시하므로, 개별 페이지 내에서는 제목과 구분선을 제거합니다.
    -   **액션 버튼**: 페이지 상단 우측에 배치하여 일관성을 유지합니다.

4.  **단순성 유지**: 명확한 필요 전까지 과도한 추상화(조기 컴포넌트 분리 등)를 지양하고, 가독성과 실용성을 우선합니다. 리팩토링 시에는 기능 변경 없이 구조 개선에만 집중합니다.

## 7. 애플리케이션 핵심 로직 (Core Application Logic)

이 섹션은 애플리케이션의 핵심 비즈니스 로직과 데이터 흐름을 정의합니다.

### 7.1. 조직 및 사용자 구조 (Organization & User Structure)

1.  **법인 (Corporation)**: 시스템의 최상위 단위입니다. (예: `바루 가먼트`)
2.  **공장 (Factory)**: 특정 법인에 소속된 생산 단위입니다. (예: `하노이 공장`) 모든 직원은 공장에 소속됩니다.
3.  **직원 (Employee)**: 특정 공장에 소속된 사용자입니다. 각 직원은 시스템 내에서 정의된 역할(Role)을 가집니다.
4.  **역할 (Role)**: 사용자의 역할과 책임을 나타내는 개념입니다. (예: 관리자, 작업자)
5.  **고객사 (Customer)**: 제품 생산을 의뢰하는 회사입니다. (예: `더산`)

### 7.2. 스타일 및 공정 관리 (Style & Process Management)

1.  **스타일 (Style)**: 특정 고객사에 속한 의류 모델입니다. 하나의 스타일에는 여러 생산 공정이 포함됩니다.
    - **이미지 관리**: 스타일 관련 이미지를 업로드 및 삭제할 수 있으며, 삭제 시 확인 절차(Confirm)를 거칩니다.
    - **데이터 통합**: 기본 정보, 공정 관리(Process), BOM 정보가 하나의 스타일 객체로 통합 관리됩니다.
2.  **공정 (Process)**: 스타일을 생산하기 위한 개별 작업 단계입니다.
3.  **공정 데이터의 흐름 (Process Data Flow)**:
    -   **공정 등록**: `속성 관리(AttProcess.jsx)` 페이지에서 표준화된 공정 목록(예: '주머니 달기', '지퍼 부착')을 등록합니다.
    -   **공정 사용**: `스타일 관리(styleProcess.jsx)` 페이지에서 새로운 스타일을 등록할 때, 미리 정의된 공정 목록을 가져와 옵션으로 사용합니다.
    -   **목표**: 모든 스타일에 걸쳐 동일한 공정에는 일관된 명칭과 기준을 사용하게 하여 데이터의 정합성을 보장합니다.
    -   **활용 계획**: 수집된 데이터를 바탕으로, 특정 의류 카테고리(예: '바지')의 특정 공정(예: '주머니 달기')에 평균적으로 소요되는 시간을 분석하고, 이를 생산성 가이드로 활용할 계획입니다.

### 7.3. 핵심 시간 관리 모델: PT / AT / ST (역할 기반)

이 모델은 PT, AT, ST 개념을 **역할 중심으로 명확히 구분**하여, 공장 간의 역할 분리와 급여 사전 합의 구조를 설명합니다. 이 섹션은 코드 구현이 아닌, 개념의 역할과 경계를 정확히 이해하는 것을 목적으로 합니다.

#### 1. 전체 설계 철학

- **사전 합의 원칙**: 급여는 '사후 정산'이 아니라 **사전 합의**를 원칙으로 합니다. 작업이 시작된 이후에는 급여 재산정이나 차감이 발생하지 않습니다.
- **데이터의 역할**: 사후에 수집된 생산 데이터(작업 기록)는 급여를 조정하거나 차감하는 데 사용되지 않습니다. 대신, **향후 작업을 위한 기준(AT, QF)을 개선하고 학습하는 데이터**로만 활용됩니다.
- **지급 기준의 단순화**: 작업자에게는 복잡한 계산 과정(AT, DT, QF 등)을 노출하지 않습니다. 작업 전 상호 합의된 **최종 지급 기준 시간(PT 또는 ST)**만 명확히 제시됩니다.

#### 2. 지급 기준: PT와 ST

**PT(Provisional Time)**와 **ST(Standard Time)**는 지급 임금을 산출하는 최종 기준으로서 **동등한 위상**을 가집니다. 어떤 기준을 사용하든, 최종 지급 임금은 아래와 같이 계산됩니다.

> `지급 임금 = 확정된 지급 기준 시간 (PT 또는 ST) × 작업 수량 × 공장의 초당 임금`

- **PT (Provisional Time, 임시 지급 기준 시간)**
  - **정의**: AT(순수 공정 시간)가 아직 없거나, 신뢰 가능한 AT가 축적되지 않은 신규/특수 작업에 대해 관리자와 작업자가 **상호 합의하여 임시로 정하는 지급 기준**입니다.
  - **역할**: AT가 없는 초기 단계의 작업을 진행하고, 그 과정에서 AT 산출을 위한 기초 데이터를 축적하는 데 사용됩니다. PT는 AT가 확정되지 않은 모든 작업에 적용할 수 있는 유연한 운영 방식입니다.

- **ST (Standard Time, 표준 지급 기준 시간)**
  - **정의**: AT와 QF를 기반으로 산출되며, 작업 전 합의하는 **표준 지급 기준 시간**입니다.
  - **산출 및 조정**: 시스템은 AT와 QF를 이용해 ST를 자동으로 계산하여 제안하지만, 관리자는 작업자 불만, 공정 난이도 등 여러 요소를 고려하여 **제안된 값을 수동으로 조정하여 최종 확정**할 수 있습니다. (예: 시스템 계산 21초 → 관리자 최종 확정 25초)

#### 3. 기준 시간 재료: AT, DT, QF

**AT, DT, QF**는 그 자체로 지급 기준이 아니며, 오직 ST를 수학적으로 산출하기 위한 **내부 계산 재료**입니다.

- **AT (Actual Time, 순수 공정 시간)**
  - **정의**: 특정 스타일의 **특정 공정 1단위**를 생산하는 데 필요한, 데드타임(Dead Time)을 제외한 **평균 순수 작업 시간**입니다.
  - **핵심 원칙: '스타일-공정' 종속성**: AT는 **'스타일-공정' 조합을 기준으로만 관리**됩니다. 동일한 공정명(예: '주머니 달기')이라도 스타일에 따라 난이도와 작업 밀도가 다르므로, AT는 절대 공유되지 않습니다. 공정명 표준화의 목적은 AT를 통일하기 위함이 아니라, 신규 스타일의 PT를 설정할 때 참고 가능한 비교 기준을 제공하기 위함입니다.
  - **산출**: 여러 작업 기록(생산량, 총 소요 시간)을 분석하여, 시스템이 통계적으로 DT를 분리하고 순수 작업 시간을 추정하여 산출합니다.

- **DT (Dead Time, 비생산 시간)**
  - **정의**: 작업 준비, 대기, 장비 전환 등 생산 수량과 직접적인 관련이 없는 모든 비생산 시간을 의미합니다. 시스템은 작업 기록을 분석하여 통계적으로 DT를 식별합니다.

- **QF (Quantity Factor, 공장별 보정 계수)**
  - **정의**: 분리된 DT 패턴 등을 바탕으로, 각 공장 고유의 생산 환경(평균 작업 배정량, 라인 효율 등)을 반영하는 **보정 계수**입니다.
  - **역할**: QF는 급여를 사후에 조정하거나 차감하는 계수가 아닙니다. AT를 기반으로, **해당 공장의 운영 현실을 반영한 ST를 "사전에 합의 가능하게 만들기 위한" 수학적 도구**입니다. 모든 조정은 작업 시작 전에 완료됩니다.


#### 4. 급여 기준 모드 설정 및 적용

유연한 운영을 위해 급여 기준은 공장별 기본값과 작업별 설정을 조합하여 결정됩니다.

1.  **공장 단위 설정 (기본값)**:
    - 각 공장 설정에서 기본 급여 기준 모드(PT 또는 ST)를 지정합니다. 이 설정은 작업 배정 시 기본으로 불러올 값을 의미합니다.

2.  **작업 배정 시점 선택 (최종 결정)**:
    - 작업 배정 시, 공장의 기본 설정(PT 또는 ST)이 자동으로 적용됩니다.
    - 하지만 관리자는 필요에 따라 **개별 작업 건에 대해 기준을 스위치(예: ST 모드이지만 AT가 없어 PT로 임시 변경)하여 최종 확정**할 수 있습니다.
    - 이렇게 **배정된 작업에 지정된 지급 기준(PT 또는 ST)과 시간이 해당 작업의 최종 지급 기준**이 됩니다.

#### 5. 핵심 용어 정리

- **PT (Provisional Time)**: AT가 없거나 불확실할 때 사용하는 **임시 지급 기준 시간**.
- **AT (Actual Time)**: **순수 공정 시간**. 여러 생산 기록에서 DT를 제외하고 산출한, 특정 `스타일-공정` 1단위를 생산하는 데 걸리는 평균 시간.
- **ST (Standard Time)**: **표준 지급 기준 시간**. AT와 QF를 기반으로 산출되며, 작업 전 합의하는 최종 급여 기준.
- **QF (Quantity Factor)**: 공장 고유의 생산 환경(작업 수량 등)을 반영하여, 사전 합의를 위한 ST를 산출하는 **보정 계수**.
- **DT (Dead Time)**: 작업 준비, 대기 등 생산 수량과 직접 관련이 없는 비생산 시간.

### 7.4. 작업 기록 관리 (Work Record Management)

작업자가 수행한 생산 내역을 입력하고 관리하는 핵심 모듈입니다.

1.  **데이터 구조 (Data Structure)**:
    -   **Master (WorkDetail)**: 작업일자, 공장 ID, 작성자(로그인 유저).
    -   **Detail (WorkerLog)**: 작업자 ID (선택된 공장 소속 직원으로 필터링).
    -   **Sub-Detail (WorkItem)**: 고객사 → 스타일 → 공정 → 수량.

2.  **입력 로직 및 제약 (Input Logic & Constraints)**:
    -   **계층적 선택 (Cascading Select)**: `고객사` 선택 시 해당 고객사의 `스타일`만 노출, `스타일` 선택 시 해당 스타일의 `공정`만 노출되는 종속적 필터링 적용.
    -   **유효성 검사**: 수량은 **양의 정수**만 입력 가능 (소수점, 음수 차단).
    -   **자동 계산**: 공정 선택 시 `공임 단가`와 `합계`(`단가 * 수량`)가 실시간으로 계산되어 읽기 전용(Read-only)으로 표시됨.
    -   **UX 편의성**: 수량 필드에서 `Enter` 키 입력 시 자동으로 다음 작업 항목 추가.

### 7.5. 작업 현황 및 효율 분석 (Work Status & Efficiency)

입력된 작업 기록을 바탕으로 공장 및 작업자의 생산성을 분석합니다.

1.  **지표 정의**:
    -   **총 작업 시간 (Total Standard Time)**: `∑ (공정별 기준 시간 * 수량)`. 공장의 급여 기준(PT 또는 ST)에 따라 계산.
    -   **총 근로 시간 (Total Working Hours)**: 작업자들의 실제 출퇴근 체류 시간 합계.
    -   **생산 효율 (Efficiency)**: `(총 작업 시간 / 총 근로 시간) * 100`. (이 지표는 ST 기준 공장에만 적용됩니다.)
2.  **시각화**:
    -   단순 초(Second) 단위가 아닌 `X시간 Y분` 형식으로 변환하여 표시.
    -   직원 1인당 평균 시간을 계산하여 제공.

### 7.6. 인증 및 사용자 세션 (Authentication & User Session)

-   **전역 상태 관리**: `AuthContext`를 통해 로그인한 사용자 정보(ID, 이름, 권한, 소속 공장 등)를 전역에서 관리합니다.
-   **데이터 연동**: 데이터 생성(예: 작업 기록) 시 현재 로그인한 사용자의 정보가 '작성자' 필드에 자동으로 매핑됩니다.

### 7.7. 스타일 신규 등록 로직 (New Style Registration Logic)

- **기본 정보 페이지 (Basic Information Page):**
  - 스타일 등록 시, `고객사` 정보를 필수로 선택해야 합니다.
  - **제품 카테고리(스타일 카테고리)**는 **`속성 관리`** 메뉴에서 미리 등록된 값을 불러와 선택합니다.
  - 기타 필요한 기준 정보들을 API를 통해 호출하여 사용합니다. (세부 항목은 추후 정의)

- **공정 정보 페이지 (Process Information Page):**
  - **평균 공정 시간 계산:** `작업 기록(Work)` 데이터를 기반으로, 공정별 평균 소요 시간을 계산하여 참고용으로 표시합니다. 단, 이 기능은 **의미 있는 예측을 위해 충분한 작업 기록 데이터가 축적되어야** 합니다.
  - **평균 시간의 분류:** 평균 시간은 위에서 선택한 `제품 카테고리`별로 분류되어야 합니다. (예: '셰프복 주머니 달기' vs '바지 주머니 달기') 이는 유사한 작업의 소요 시간을 예측하는 데 사용됩니다.
  - **공정 종류 표준화:** `기준 정보`에 미리 정의된 `공정 종류` 목록을 호출하여 사용자가 선택하도록 합니다. 이를 통해 '주머니 달기'와 같은 공통된 작업에 일관된 명칭을 사용합니다.

- **BOM (Bill of Materials) 페이지:**
  - BOM 정보는 추후 개발될 `재고 관리` 기능과 연동될 예정입니다.

## 8. UI 패턴 (UI Patterns)

*이 섹션은 반복적으로 사용되는 UI 컴포넌트의 표준 구현 방식을 정의합니다.*

### 8.1. 데이터 테이블 (Data Table)
- **개요**: 목록 화면에서 데이터를 표시하는 표준 테이블 구조입니다. '스타일 관리' 페이지의 구현을 기준으로 통일합니다.
- **구조 정의**:
  - **컨테이너**: `<Paper variant="outlined">`를 사용하여 그림자 없는 테두리 스타일을 적용합니다.
  - **헤더**: `<TableHead>`에 `sx={{ backgroundColor: '#f5f5f5' }}`를 적용하여 본문과 구분합니다.
  - **헤더 폰트**: 헤더 셀(`<TableCell>`)에는 `sx={{ fontWeight: 'bold' }}`를 적용합니다.
  
  ```jsx
  <Paper variant="outlined" sx={{ width: '100%' }}>
    <TableContainer>
      <Table stickyHeader size="small">
        <TableHead sx={{ backgroundColor: '#f5f5f5' }}>
          <TableRow>
            <TableCell sx={{ fontWeight: 'bold' }}>컬럼명</TableCell>
            ...
  ```
