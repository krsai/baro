# 공통 UI 사용 기준

- 물리 부피(CBM) 편집은 `VolumeInput`으로 통일한다. 숫자와 안전한 사칙연산 수식을 허용하고 계산값/원문을 함께 전달한다. 평소에는 계산값과 빈 값의 0 표시, hover·focus에는 수식 원문을 제공한다. 수량은 자동으로 곱하지 않으며 수량보다 적은 합산 항목 안내는 공통 상단 경고로 표시하고 저장을 막지 않는다. 별도 L/W/H 입력은 제공하지 않는다. 새 운송 화물 요약은 화물명→수량→단위→중량→부피 다섯 칸과 모바일 두 열 배치를 유지한다. 기존 값/snapshot은 화면 기본값으로 일괄 수정하지 않는다.

- 완료·청구 완료·지급 완료의 포함 여부는 SEARCH 안의 `CompletionFilter` 선택 필터(제외/포함)로 표시한다. 스위치·체크박스로 별도 강조하지 않으며 기존 화면의 완료 판정·기본값·초기화·조회 범위는 유지한다. 제목 아래의 반복 설명·입력 안내·기준 시각·선택 필터와 중복되는 부제목은 표시하지 않는다. 실제 업무 상태·수량·확정 이력·조회 실패와 필요한 선택/확인 절차는 보존한다. 개별 CSS로 숨기지 않고 해당 표시 소스와 공통 컴포넌트에서 정리한다.

- 배정 편집 이력 작업 예외: 되돌리기·다시하기·배정 초기화는 조회 조건이 아니므로 SEARCH 카드 바깥 바로 아래에 별도 우측 정렬 행으로 배치한다. 좁은 화면에서는 줄바꿈하며 검색 조건을 접어도 유지한다. SEARCH 안의 조회 초기화와 상단 저장은 각자의 기존 범위에 둔다. 기존 편집 이력·포커스 보존·비활성/저장 중 조건은 변경하지 않는다.

한 줄 입력과 가로 ToggleButtonGroup은 바깥 높이를 기본 36px·컴팩트 32px로 맞춘다(터치 환경 36px). 그룹의 테두리·내부 여백도 높이에 포함한다. 입력값과 축소 전 outlined 라벨은 세로 중앙에 배치하고 체크/스위치 라벨은 공통 글자 크기·행간으로 중앙 정렬한다. 여러 줄 입력과 세로 선택 그룹은 내용 높이를 유지하며 축소 라벨·notch는 기존 MUI 계약을 따른다. 높이 보정은 개별 화면 대신 공통 테마에서 관리한다.

그리드로 줄바꿈하는 선택 그룹은 고정 전체 높이를 강제하지 않는다. TransportModeSwitch·운송 고객 역할 그룹은 공통 높이에서 테두리/패딩을 뺀 최소 행 높이를 사용하고 문구가 여러 줄이면 그룹 전체가 함께 늘어난다. 자식에 별도 36px 최소 높이를 넣어 컴팩트 그룹 밖으로 밀어내지 않는다. 검수는 바깥 높이뿐 아니라 실제 자식 버튼의 사각형 포함·문구 잘림·다음 입력과 겹침을 기본/컴팩트·PC/모바일에서 확인한다.

- 컴팩트는 짙은 탐색 메뉴·각진 패널·청회색 작업 배경·명확한 표 헤더·6px 간격 체계를 사용하는 별도 관리 앱 디자인이다. 기본 테마와 글자 크기·업무 상태색·터치 조작·초안·문서 스타일은 유지한다. 개인·회사별 선택과 즉시 전환은 기존 공통 테마 계층에서 관리한다.

- 운송 업무는 PC 왼쪽에 당사자/구간/화물, 오른쪽에 업무 정보/일정/거래·운임 조건/비고를 배치하며 모바일에서도 당사자부터 세로로 이어진다. 전체 너비의 상단 작업은 MBL/HBL·AR/AP·서류다. 업무 정보는 고객·SR 일자·업무 담당자로 한정하고 운송 방식 배지를 붙이지 않는다. Cargo Ready Date는 일정 영역에 두며 공통 MBL 연결 후에도 업무별 준비일은 편집할 수 있다. 화물은 PC에서 이름·수량·단위·총중량·부피를 같은 행, 컨테이너 규격/포장별 치수를 아래에 둔다. 좁은 화면은 이름 전체 너비와 수치 두 열로 줄바꿈하며 기존 여러 줄 화물 원문은 유지한다. 문서 인쇄 양식을 그대로 편집 폼으로 재사용하지 않는다. 당사자 라벨은 세 언어 모두 Shipper / Consignee / Notify Party다. 의뢰 입력의 라벨과 별도 제목행을 중복하지 않으며 기본 Notify 연동에 별도 체크박스를 요구하지 않는다.

- 운송 업무는 의뢰의 실제 당사자·주소/연락처·구간·화물·조건을 본문에 표시하고 내부 페이지 탭으로 분산하지 않는다. 요청하지 않은 진행 탭/단계 UI를 추가하지 않는다. MBL/HBL 편집은 본문의 실제 연결에서 AppDialog로 열고 닫아도 업무 입력은 보존한다. 목록과 운송건별 상위 업무 탭은 유지한다.

- 운송 상세의 상단 전체 작업 줄은 운송 상세→MBL/HBL→AR/AP→서류 순서다. 운송 상세 버튼은 펼친 BL 연결 목록을 접고 본문으로 복귀하며 BL/서류·AR/AP 편집창 상단에도 명시적 ‘운송 상세로 돌아가기’를 제공한다. 하단 닫기·Esc와 기존 미저장 확인을 유지하고 상세 본문을 재생성하지 않는다. 저장 중/결과 불명 상태를 무시하고 복귀하지 않는다.

- 운송 목록은 날짜를 첫 열에 두며 운송 방식은 FCL/LCL로 표시한다. 출발지·도착지는 실제 업무 범위 지점의 저장된 대표명(label)을 우선하고 없으면 기존 주소를 표시한다. 마지막 오른쪽 고정 SR 열은 문서 아이콘이며 툴팁·접근성 이름으로 ‘SR 보기’를 제공한다. 원본 의뢰는 읽기 전용 AppDialog로 조회하고 원본 없음/조회 실패를 업무 편집폼으로 대체하지 않는다. 버튼 이벤트는 행의 더블클릭·키보드 업무 탭 진입과 분리하며 목록 검색/페이지·열린 업무 탭을 보존한다.

- 운송 업무 Route는 해당 지점의 저장된 대표명과 주소를 `대표명 (주소)`로 표시한다. 대표명이 없으면 주소를 유지하고 표시 조합을 주소 원문으로 저장하지 않는다. 저장된 지점 날짜가 현지 오늘보다 이전이면 번호 원을 공통 primary 색으로 채운다. 오늘·미래·빈 날짜·미저장 초안은 미진행이다. 열어둔 화면의 날짜 경과도 반영하되 운송 상태·서류·원본·snapshot을 자동 저장하지 않는다. 증빙 첨부/연결은 최신 사용자 지시로 제외한다.

- 운송 상세의 FCL 컨테이너 길이/타입/대수는 오른쪽 별도 패널로 분리하고 왼쪽 화물 요약 행과 섞지 않는다. 구간의 주소와 읽기 전용 항만/공항은 같은 칸 틀을 사용하고 최소 한 줄에서 실제 내용에 맞춰 늘어난다. 빈 3줄 주소 칸을 강제하지 않으며 기존 여러 줄 원문과 세로 흐름/순번은 유지한다. 아래 이전 컨테이너/화물 순서보다 이 상세 화면 정정이 우선하고 SR 입력의 배치는 별도다.

- 운송 상세의 당사자는 Shipper→Consignee→Notify Party의 같은 너비 세로 배치다. 운송 구간은 실제 저장된 업무 범위에 따라 출발지→출발 항만/공항→도착 항만/공항→도착지의 2~4칸을 세로로 연결한다. 시작/끝의 기존 편집과 중간 항만/공항 FK는 유지한다. 구간 범위가 없는 과거 자료는 주소 두 칸과 저장된 중간 지점만 표시하며 이름으로 지점을 합치지 않는다. FCL 화물은 컨테이너 규격·대수가 먼저이고 그 아래에 화물명·수량·단위·총중량·부피 한 행이다. 포장별 치수는 요약 행 아래를 유지한다. 위 이전 컨테이너/요약 순서보다 이 최신 사용자 선택이 우선한다.

- SR도 컨테이너 입력 아래에 화물명·수량·단위·총중량·총부피의 공통 높이 요약 행을 제공한다. 화물명은 직접 입력과 ShippingCommodityInput의 공통 검색/목록·상세 선택을 함께 제공하고 포커스/타이핑만으로 HS를 추정 적용하지 않는다. 직접 입력한 완성 총량은 포장별 치수와 독립이며 ‘치수 합계 적용’ 때만 치수 계산값으로 교체한다. 포장 단위는 코드 원문을 보존한다. Cargo Ready는 선택적 화물 준비 일정 접기에 두고 값이 있으면 기본 펼침으로 보존한다.

- 운송 업무의 기본 화면은 공통 MBL과 자기 업무 HBL의 실제 연결·등록·열기 작업을 가까이 배치한다. 기존 MBL 선택은 ListDetailDialog의 목록/상세와 명시적 연결 버튼을 사용한다. 공통 선박/일정은 MBL에서 관리하고 업무별로 중복 입력하지 않는다. 등록 업무에 속한 MBL 금액을 다른 연결 업무의 0원 금액처럼 표시하지 않는다. 입력 필드를 늘려 빈 공간을 채우지 않는다.

- 일반 텍스트의 단어 안에 대문자가 2개 이상 포함되고 SYSTEM 약어 사전에 등록된 경우에만 등록 표기를 보존한다. `BOM`·`iOS`·`SaaS`는 보존하고 `bom`·`Bom`은 `Bom`, 미등록 `COTTON`은 `Cotton`으로 처리한다. 약어·풀어쓴 이름·뜻은 SYSTEM에서 관리하며 풀어쓴 이름·뜻은 선택 입력이다. 사전의 원문 입력에는 `data-text-case="preserve"`를 사용한다. 사전 갱신은 열린 업무 초안을 변경하지 않으며 최초 로딩 실패 시 편집 대신 재시도를 제공한다.

- 일반 영문·베트남어 표시 문구와 이름·담당자·주소·설명은 단어별 첫 글자를 대문자로 쓴다(Title Case, 띄어쓰기 유지). 회사명은 기존 대문자 규칙, 코드·약어·통화·식별자·이메일·URL·검색어는 기존 형식을 유지한다. `BusinessTextInput`은 편집 가능한 일반 TextField의 기존 값을 Title Case로 표시하되 조회·포커스·미변경 blur만으로 onChange·저장·dirty를 만들지 않는다. 실제 입력 중에는 커서·IME 원문을 유지하고 입력 완료 시 실제 값을 정리한다. 외부 라벨 입력도 name/aria-label로 분류하며 원문·읽기 전용/발행 snapshot 입력은 보존한다. 개별 폼에서 표시용 상태를 복제하지 않는다. 특수 원문 입력은 `data-text-case="preserve"`, 명시적 일반 텍스트 입력은 `data-text-case="title"`을 사용한다. 새 JSON 저장은 클라이언트·서버의 동일한 `humanTextCase` 분류를 거치며 키·enum·불변 snapshot·파일 내용은 변환하지 않는다.

- 목록·상세의 담당자/대표자/직원명·주소는 `humanTextDisplay`로 표시만 정리한다. 공통 목록의 모호한 name 열은 회사명을 포함할 수 있으므로 자동 변환하지 않으며 개인 이름 열은 `textCase: 'title'`, 보존할 원문 열은 `textCase: 'preserve'`를 명시한다. 공통 선택의 검색어·정확 일치·선택 원본은 표시 변환으로 바꾸지 않는다.
- 목록에서 선택한 저장 항목은 실제 ID와 revision을 유지해 수정하며 대표 버튼도 수정으로 표시한다. 새 항목·등록 원본에서의 복사는 신규 저장으로 구분하고 원본 수정/삭제 권한을 주지 않는다. 행 ID 유무만으로 수정 여부를 추측하지 않는다(신규 초안도 UUID가 있을 수 있다). 주소록·운송 당사자·특송 일반 고객은 서버 version으로 구분한다. 문서 적용/불러오기는 원본 저장과 별도다.

- 국가/전화 입력은 `EntityCountryField`와 거래처 공통 `EntityPhoneField`를 재사용한다. 국가 값은 공통 사전의 ISO 코드이며 화면에서 국가번호를 보여준다. 운송의 숫자 전용 입력·본문/국가 분리 저장은 `digitsOnly`/`localValue` 옵션으로 명시하고 다른 거래처 폼의 국제번호 저장 계약을 바꾸지 않는다. 기존 값은 조회만으로 정규화하지 않으며 같은 양식 사용이 업체 자동 연결이나 일반 거래처 생성을 의미하지 않는다.

- 목록 선택과 상세/등록/수정이 같은 업무라면 최초 선택 입력에서 `ListDetailDialog`로 직접 진입한다. 단일 상세창을 먼저 띄우고 다시 주소록/관리창을 여는 중복 단계를 만들지 않는다. 운송 SHPR/CNEE/NOTIFY·특송 일반 고객·FCL 항구/운송지가 적용 예다. 원본 저장과 문서 적용의 범위는 유지하고 상세 미리보기 자체로 저장하거나 적용하지 않는다. 항구/공항의 공식 코드는 공식 목록에서 선택하며 새 항구 등록 권한을 고객 주소록 기능으로 확대하지 않는다.

## 표의 조회 상태와 페이지 이동

- 일반 표의 빈 자료·조회 중·실패·조회 대상 미선택은 `TableStatusRow`를 사용한다. 정상 빈 결과의 문구는 한영베 공통 사전의 “표시할 자료가 없습니다.”이며 전체 열을 차지하는 가운데 정렬, 최소 84px 상태 영역을 유지한다. 긴 업무 설명을 넣어 표마다 높이가 달라지게 하지 않는다. 실제 선택 절차에 필요한 문구는 `message`로 보존한다.
- `loading`, `error`, `loaded`, `onRetry`를 실제 조회 상태에 연결한다. 실패를 빈 자료로 표시하지 않는다. 실패한 요청의 재시도는 실제 API를 다시 호출해야 한다. `languageCode`를 전달하거나 LanguageProvider 안에서 사용한다. 상태 행의 `data-table-status`는 작업 열 자동 고정에서 제외한다. 그렇지 않으면 재시도 버튼이 마지막 작업 열로 오인되어 전체 상태 셀이 고정될 수 있다.
- 단순 이전/다음 이동은 `ListPagination`을 사용한다. 실제 cursor·페이지·전체 개수·활성 조건은 호출부가 소유하고, 공통 컴포넌트는 정렬·간격·접근 가능한 이름만 제공한다. 합계는 `leading`, 현재 페이지는 children에 둔다. 행 개수 선택이 필요한 `TablePagination`, 월 이동, 적용 버전 선택은 각각 기존 공통 컴포넌트를 유지한다. 빈 자료를 감추려고 가짜 페이지나 총개수를 만들지 않는다.
- 펼친 행의 편집폼·하위 표·행별 입력 오류는 조회 상태가 아니다. 읽기 전용 설명 모달, 본문에서 개별 저장하는 작업창, 후보별 승인/거절 창은 하단 저장/취소를 임의로 추가하지 않는다. 안내를 위해 빈 상세 폼을 만들지 않는다.
- `npm run check:ui-consistency`는 전체 JSX의 중복 상태 행·단순 페이지 이동·직접 MUI 검색 선택/알림·native select/dialog를 검사한다. `--report`는 모달의 직접 하단 작업 유무 등 수동 검토 후보도 출력한다. 정적 검사는 모든 업무 상태의 실제 실행 검증을 대신하지 않는다. 새 예외는 업무상 이유와 기존 공통 계층으로 처리할 수 없는 점을 검토하고 문서화한다.
- 이 구조는 문구와 외형을 페이지마다 복사하지 않고 다음 개발에도 적용하기 위한 것이다. 높이·정렬·페이지 이동 위치 변경 요청은 공통 토큰/컴포넌트에서 먼저 검토한다. 출력 서류·편집 표·업무 승인 흐름까지 한꺼번에 바꾸면 생기는 영향을 설명하고 예외가 필요한 경우 해당 범위만 제안한다.

## 청구서 등록 입력 정렬

- 청구서 번호·청구일은 `InvoiceFormHeader`의 제목 줄 오른쪽에 나란히 두고 모바일에서는 제목 아래로 배치한다. 외부 라벨·36px 입력·테두리 계약을 같은 헤더 안에서 적용한다. `InvoiceEntrySettings`는 청구 유형·대상 선택만 담는다. 일반 청구 통화는 각 입력 행의 별도 선택 열이며 첫 행 기본값은 VND, 새 행은 추가한 위치의 직전 행 통화를 상속한다. 각 행은 독립 변경 가능하고 서로 다른 통화의 금액을 더하거나 자동 환산하지 않는다. 합계·발행 문서·수금/잔액은 통화별로 구분하며 기존 단일 통화 발행 snapshot은 보존한다. 주문 청구는 실제 주문 단가·통화 FK 계약을 유지한다.
- 편집용 문서 필드는 `InvoiceDocumentField appearance="form"`을 사용한다. 외부 라벨은 12px/16px 행 높이, 입력과의 간격은 6px, 입력은 공통 36px 높이다. 회사 정보는 ① 회사명·사업자번호 ② 전체 폭 주소 ③ 담당자·연락처·이메일의 세 행이다. SaaS 내부 회사 코드는 표시하지 않으며 기존 FK·코드 저장값은 보존한다. `invoicePartyLayout.mjs`가 물류/봉제·주문/일반 청구의 편집·상세·HTML/PDF 출력에서 같은 필드 순서를 제공한다. 담당자는 문서의 연락 담당자이며 직원 개인정보를 자동 조회하지 않는다. 문서 안에서 수정하는 값이며 회사 원본이나 기존 발행 snapshot을 갱신하지 않는다.
- 품목 표는 머리글을 시각적 라벨로 쓰고 입력 자체의 접근 가능한 이름은 유지한다. 설명은 가변 폭, 수량·통화 금액·세율은 필요한 폭과 우측 정렬을 확보한다. 행마다 라벨/placeholder가 달라 입력칸의 높이나 위치가 바뀌지 않게 한다. 좁은 화면에서는 표 내부 스크롤로 전체 금액과 작업 열을 보존한다.
- 이 편집용 배치는 읽기 전용 문서/출력 CSS와 구분한다. 단지 정렬을 맞추기 위해 주소 원문·통화 정책·반올림·VAT·대표 계좌·발행/개정 정책을 변경하지 않는다.

## 목록과 상세·수정의 좌우 배치

- 운송의 SR 확인과 포워더 업무 상세는 별도 단계다. 포워더 목록 더블클릭/키보드 진입은 SR, 고객 SR 접수 성공 후 B/L 선택→운송 상세로 이동한다. 포워더 직접 등록은 저장 확인 후 접수 단계를 생략한다. 운송 상세 안에서 서류를 출력하고 One Master는 Master, Master+House는 House에 DC를 입력한다. 기존 원본/FK·회사 범위·미저장/결과 불명 보호를 유지하며 목록/고객 공유 버튼을 다시 추가하지 않는다.

- 앱의 기존 자료 진입은 **메뉴 → 목록 → 상세**다. 메뉴는 업무 이름, 목록/상세 제목은 같은 업무 이름에 목록/상세를 붙인다. 상세에서 권한·현재 상태가 허용하는 값을 직접 입력하고 `저장`을 눌러 반영한다. 별도 수정 화면·수정 모드 진입을 기본 단계로 추가하지 않고, 같은 원본의 조회와 수정을 나누지 않는다. 목록의 원본 진입 작업과 아이콘도 상세로 표시한다. 등록·결재·발행/개정·취소/삭제는 실제 업무 동작으로 구분하며 기존 권한·revision·snapshot·저장 범위를 유지한다. 거래 내역 등 연결 정보는 해당 상세 안에서 조회한다. 설정 단일 폼·분석 화면·대량 입력표에 가짜 목록을 추가하지 않는다.

- 항목을 골라 정보를 확인하거나 선택 항목의 설정을 수정하는 화면은 `ListDetailLayout`을 우선 사용한다. 왼쪽은 검색 결과/분류/항목 목록, 오른쪽은 선택 항목의 실제 정보·연결 관계·편집 영역이다. 선택 대상을 보면서 내용을 확인할 수 있고, 펼친 행 때문에 목록 위치가 크게 움직이는 일을 줄이기 위한 구조다. 오른쪽을 채우려고 일반 안내문·가짜 설명·빈 편집폼을 만들지 않는다.
- 기본은 PC 좌우, 작은 화면은 목록→상세 순서의 세로 배치다. 일반 선택창은 1:1, 분류 목록은 240px+본문, 넓은 공정 입력 표는 xl부터 1.3:1로 나눈다. 각 pane의 minWidth:0을 유지하고 넓은 표는 pane 내부에서 스크롤한다. 글자·금액을 줄이거나 생략해 두 칸에 맞추지 않는다.
- `LookupSearchDialog`는 기존 `details`를 우선 보존한다. 3개 이상 표시 열이 있는 선택창은 그 열의 `value`만 `RecordDetails`로 미리 보여준다. 자재·스타일·증빙·기초 잔액·상세 열이 있는 공통 선택창에 적용되며, 서버 응답 객체의 임의 속성을 열거하거나 추가 조회/권한 확대를 하지 않는다. 표시 열 외에 필요한 정보는 호출부가 `renderDetails(row)`/`renderLookupDetails(row)`로 명시한다. 단순 코드·이름 선택은 전체 목록 폭을 유지한다. 중복 정보만 생기거나 넓은 표가 핵심이면 `previewDetails={false}`로 제외할 수 있다.
- 자동 미리보기의 첫 항목은 현재 페이지의 조회 후보일 뿐 확정값이 아니다. 마우스로 행을 가리키기·클릭·키보드 포커스·방향키는 미리보기를 바꾸고 기존 선택 버튼/허용된 Enter·더블클릭만 확정한다. 마우스 미리보기는 검색 입력의 실제 포커스를 옮기지 않으며 비활성 후보·터치 스크롤로 확정하지 않는다. 미리보기 때문에 Enter/Tab 정확 일치·IME·다중 선택·취소·포커스 복귀 규칙을 바꾸지 않는다. 로딩/조회 실패를 정상 상세나 빈 편집폼으로 위장하지 않는다.
- `HierarchyPanel`은 동일한 공통 배치로 회계 코드·세부 업종 분류 목록과 실제 오른쪽 내용을 연결한다. 정적 사전은 그룹을 선택해 항목을 조회한다. 공정 대상/동작 기준정보의 연결 규격 편집은 선택 행 아래 대신 우측(작은 화면에서는 아래)에 표시하고 원래 수정 초안·실제 관계·삭제 제한·상단 전체 저장을 유지한다.
- 목록 선택만으로 저장하거나 초안을 초기화하지 않는다. 서로 다른 원본을 전환하는 편집기는 기존 미저장 확인을 유지한다. 한 문서의 항목별 초안은 선택을 바꿔도 보존한다. 대량 입력표·문서 편집·결재 권한 매트릭스·단일 폼·확인 모달은 업무상 목록/상세 관계가 있을 때만 전환한다. 변경 요청에는 읽기 공간·표 폭·모바일·초안 전환에 미치는 영향을 설명하고 사용자 선택을 우선한다.

## 페이지·모달 작업 버튼 계약과 선택 이유

- 운송 목록(`/shipping`)과 접수 후 상세(`/shipping/:jobId`)는 서로 다른 업무 탭이다. 목록 더블클릭·Enter/Space와 접수/직접 등록 후 이동은 공통 navigateToPath를 사용한다. 상세 내부 탭은 stage 쿼리로만 전환하며 목록과 상세의 인스턴스·검색 조건·초안은 공통 탭 보존 계약을 따른다. 같은 ID의 상세 탭을 중복 생성하지 않는다.

- 운송 상세의 내부 탭은 기존 MUI Tabs/Tab 테마를 사용하고 탭 바로 아래의 단일 Paper 본문과 연결한다. 탭만 감싼 별도 카드·본문과의 공백을 두지 않는다. 운송 업무는 의뢰 요약과 별도 최소 업무 폼으로 구성하며 서류 탭의 MBL/HBL 추가는 PageSectionHeader의 한 작업 행으로 묶는다. BL 타입/구성 선택은 제공하지 않는다. BL 입력은 일반 TextField를 사용한다. 페이지의 DialogDetailPanel 재사용 시 모달용 maxHeight·내부 스크롤을 해제해 페이지 본문이 스크롤되도록 하며, 폼별 저장·초안/재시도는 유지한다.

- 운송 SR의 최신 예외: `/shipping?id=`는 목록 위 의뢰 모달이며 접수 작업을 모달 하단에서 제공한다. `stage=bills/documents`는 운송 상세 페이지다. 기존 SR도 신규 의뢰 모달과 같은 폼·초안 보호를 사용한다.

- 모달의 기본 진입점은 `AppDialog`다. MUI `Dialog`를 개별 화면에서 직접 가져오지 않는다. 제목/본문/하단 여백·작은 화면 줄바꿈·본문 스크롤과 전체 화면 처리를 공통 테마에서 적용한다. 기존 `maxWidth`·문서 전용 너비·전체 화면·portal/ref·닫기/미저장 확인·권한/저장 조건은 호출부가 보존한다. 날짜 선택기 등 라이브러리 내부 모달에도 같은 Dialog 테마가 적용된다.
- 목록을 골라 상세를 보거나 등록/수정하는 모달은 `ListDetailDialog`를 사용한다. 운송 주소록의 선택/저장 흐름과 지급 대상 선택창의 검색/표/상세 디자인을 결합한 공통 틀이다. 제목에는 전체 작업, 본문 상단에는 검색/조회 도구, PC에는 왼쪽 목록·오른쪽 실제 상세, 모바일에는 목록 다음 상세를 둔다. `list`, `detail`, `search`, `tools`, `titleActions`, `actions`는 실제 업무 UI를 전달하는 슬롯이며 공통 틀이 API 호출·첫 항목 확정·자동 저장·삭제 권한을 추정하지 않는다. 목록 미리보기와 최종 선택은 구분한다.
- `DialogRecordList`는 마우스 포인터·키보드 포커스의 `onPreview`로 오른쪽 상세를 즉시 보여주고 방향키로 후보를 이동한다. `onPreview` 기본값은 기존 `onSelect`이며 미리보기와 클릭 동작이 다르면 별도로 전달한다. 편집 폼은 `previewDisabled={dirty}`로 미저장 초안을 지키고 명시적 클릭 전환의 기존 폐기 확인을 유지한다. `ListDetailDialog`는 검색칸/목록의 Enter만 현재 미리보기와 일치하는 행에 대해 하단 `PageActions`의 명시적 `primary` 불러오기/적용을 실행한다. 아직 후보를 포커스하지 않았다면 첫 Enter는 첫 후보를 미리 보여준다. 상세 입력칸·제목/원본 저장/삭제·IME·수정 키·반복 Enter·중첩 모달은 이 처리로 확정하지 않으며 비활성 대표 작업을 우회하지 않는다. 불변 ID는 `getKey`로 전달하고 이름으로 합치지 않는다. 조회 전용 `LookupSearchDialog`의 페이지 이동·복수 선택·정확 일치·IME·포커스 규칙은 유지한다.
- 오른쪽 상세는 `DialogDetailPanel`을 쓴다. 지급 대상·청구 대상·일반 검색의 읽기 전용 상세와 운송 주소/고객 편집이 같은 테두리·안쪽 여백·스크롤·고정 상세 작업 영역을 공유한다. 새 항목은 제목 오른쪽의 글자 있는 추가 버튼, 기존 항목의 삭제는 상세 작업 영역 왼쪽의 빨간 아이콘+글자, 등록/수정 저장은 오른쪽 대표 버튼으로 둔다. `DialogRecordActions`가 이 배치를 제공하며 기존 삭제 확인·참조 보호·미저장 확인은 호출부가 유지한다. 지원하지 않는 저장/삭제 콜백은 생략하고 가짜 버튼을 만들지 않는다.
- 고객/주소록 원본 저장과 현재 문서에 불러오기는 서로 다른 작업이다. 원본 저장/삭제는 상세 아래, 닫기→선택/확인은 모달 하단에 둔다. 일반 단일 폼의 저장은 모달 하단으로 두며 운송 의뢰도 이 규칙을 사용한다. 인쇄·이미지 복사 같은 문서 작업은 제목에 유지할 수 있고, 내부 컴포넌트가 하단 저장을 소유하는 관리 대상 설정·단계별 입력·승인·문서 전용 화면의 저장 범위를 모양만 맞추려고 합치지 않는다.
- `ui.dialog`의 폭/높이/패널 높이 토큰을 사용하고 입력폼의 큰 임의 높이나 페이지별 복사한 Dialog CSS를 새로 만들지 않는다. 모달 본문과 표/상세의 내부 스크롤을 구분하고 하단 작업을 가리지 않는다. `check:ui-consistency`가 AppDialog 외 직접 MUI Dialog import를 차단하며 `dialog-shell-browser.test.mjs`는 한영베 일반 폼/관리/전체 화면의 좁은 화면·낮은 화면·중첩 초안·정렬을 검사한다.

- 일반 페이지는 `AppPageContainer`의 `title`·`context`·`titleActions`를 사용한다. 제목·짧은 상태·페이지 전체 작업만 상단에 고정한다. 검색·날짜·필터는 `toolbar` 또는 본문으로 보내며 고정 제목에 넣지 않는다. 긴 페이지에서 저장을 찾으려고 이동하는 일을 줄이면서 검색 조건까지 고정되어 작업 공간이 줄어드는 것을 방지하기 위한 구조다.
- `/shipping`은 공통 메뉴명에 목록/상세를 붙인다. `?id=`가 있는 조회는 상세이며 운송건 번호·상태는 `context`로 구분한다. 모달의 `form=new/edit`나 업무 단계 탭으로 페이지 제목을 바꾸지 않는다. 운송 목록은 번호 버튼뿐 아니라 행 클릭·Enter/Space로 동일한 상세에 진입하며, 자식 버튼 이벤트를 중복 실행하지 않는다. 내부 원가·공유·접수 정책은 화면 정리로 바꾸지 않는다.
- 페이지 전체 추가·저장은 제목 오른쪽, 표의 행 추가는 해당 표 도구 또는 행 작업 칸에 둔다. 저장 버튼을 위아래 중복 생성하지 않는다. 모바일은 제목 다음 줄의 오른쪽 정렬과 줄바꿈을 허용한다. 번역 문구를 줄이거나 버튼 글자를 잘라 한 줄을 강제하지 않는다.
- `PageActions`는 보조 작업(`secondary`) → 기타 작업(`children`) → 대표 작업(`primary`) 순서와 공통 간격을 제공한다. 취소·이전·닫기는 보조, 저장·선택·다음은 대표 작업이다. 저장은 `SaveButton`을 쓴다. 이 컴포넌트는 저장 API·권한·확인·취소 동작을 추측하거나 생성하지 않는다.
- 등록·편집 모달은 `DialogTitle` → `DialogContent` → `DialogActions` 구조를 쓴다. 공통 테마가 제목과 하단 작업 영역을 유지하고 본문을 스크롤한다. 하단 오른쪽에 취소 → 저장 또는 취소 → 선택을 배치한다. 조회 종료는 닫기, 작성 포기는 취소로 구별한다. 확인 대신 삭제·신청·승인처럼 실제 행동을 이름으로 사용한다. 위험 행동은 대표 저장과 구별하며 기존 확인 절차를 유지한다.
- `header`는 짧은 맞춤 제목 행의 호환 진입점이다. 검색·필터·기본 정보까지 묶지 않는다. `stickyHeader={false}`는 독립 스크롤 전문 편집기 등 근거가 있는 예외에서만 사용하고 해당 화면의 이유를 기록한다. 공통 제목 높이를 고정 숫자로 가정해 표 머리글의 `top`을 추가하지 않는다.
- 예외: 기초 잔액의 하단 저장·행 추가, 탭별 저장, 단계별 이전/다음, 배정판의 독립 스크롤, 문서 외부 저장/출력 작업은 각각 기존 업무 계약을 보존한다. 같은 모양을 만들기 위해 저장 범위·승인·발행·취소 의미를 바꾸지 않는다. 모달 제목의 보조 추가 작업도 하단 저장과 역할이 다르면 유지한다. 일반 페이지 계약은 공통 컨테이너 사용 화면에 적용되며 별도 편집기는 명시적으로 전환해야 한다.
- 추후 변경 요청에는 고정 영역의 높이, 긴 표/문서의 가시 영역, 탭별 저장 범위, 모바일·한영베 줄바꿈, 미저장 이탈 보호에 미치는 영향을 먼저 설명하고 대안을 조언한다. 이 규칙을 영구 고정하거나 새로운 승인 절차로 삼지 않는다. 사용자의 최신 선택이 우선하며 변경은 공통 계층과 이 계약에 함께 반영한다.

## 기능 설명 정보 버튼

설정의 의미를 설명할 때는 `InformationButton`을 제목/라벨 옆에 둔다. 설명은 기능별 다국어 `{ko,en,vi}` 콘텐츠의 `title`과 `paragraphs`로 관리하며 현재 화면 언어로 표시한다. 마우스 호버에만 의존하지 않고 클릭·Enter·Space로 설명창을 열고 하단 닫기 버튼 없이 배경 클릭/Escape로 닫으며 원래 버튼으로 포커스를 돌려준다. 설명창을 열어 설정을 변경하거나 API 저장을 실행하지 않는다. `informationContent.js`의 거래처별 취급 코드 설명을 최초 적용 예로 사용한다. 실제 건수·사용 내역 조회 버튼은 이 개념 설명 버튼과 구분하고 같은 상세창을 여는 중복 아이콘은 추가하지 않는다.

## 일반 조회 카드·선택창 규격

국가와 해당 전화번호는 `EntityCountryPhoneFields` 전체가 일반 입력 한 칸을 차지한다. 이름·국가/전화·이메일처럼 한 행에 배치하면 바깥 너비는 1:1:1이며 국가/전화만 두 칸을 차지하지 않는다. 묶음 안은 8px 간격의 국가 약 30%·전화 약 70%로 같은 줄을 유지하고, 좁은 화면에서는 바깥 논리 입력들만 세로로 배치한다. 단일 상세 폼의 이름·국가/전화·주소는 각각 같은 전체 너비를 사용할 수 있다. 공식 국가 잠금과 기존 변경 콜백을 유지한다.

모든 전화 입력은 `EntityPhoneField`를 사용한다. 국내 형식으로 숫자만 입력하고 국가별 metadata로 구분 기호를 표시하며, 예시 placeholder와 숫자 입력 안내 title·숫자 키패드를 공통 제공한다. 최신 사용자 선택에 따라 화면 표시는 `+82 010-1234-5678`처럼 국가번호와 국내 형식(앞자리 0 포함)을 함께 사용한다. 표시 구분 기호는 운송의 숫자 본문에 저장하지 않으며 회사의 국제번호 저장 계약·기존 원문·문서 snapshot을 조회만으로 재작성하지 않는다. 입력 도중 앞자리 0·커서·선택/중간 삭제를 보존하고 국가/문자열로 회사 identity를 추정하지 않는다.

업무 화면 상단에서 해당 화면의 설정 창을 여는 버튼은 `PageSettingsButton`의 기어 아이콘을 사용한다. 화면에는 아이콘만 표시하고, 각 설정 이름은 현행 언어의 툴팁과 접근 가능한 버튼 이름으로 제공한다.

입력폼 안에서 현재 작성 중인 행만 거르는 검색은 표 내부 도구로 배치한다. 별도의 `SEARCH / 조회 조건` 카드를 사용하지 않으며, 저장되는 작업 기간·공장 등의 기본 정보와 구분한다. 작업 기록 입력은 기본 정보 → 행 검색·작업 표 → 비고 순서로 구성한다.

일반 목록의 검색은 `SearchPanel`을 공통 사용한다. 제목은 `SEARCH / 조회 조건` 구조를 항상 표시한다. 왼쪽은 검색어 → 일반 조회 조건(`controls`)·필터(`filters`), 오른쪽은 날짜/기간(`dates`) → 초기화(`onReset`) 순서다. 일반 필터는 검색창 바로 오른쪽에 필요한 개수만큼 붙이고 늘려 빈 공간을 채우지 않는다. 날짜·월·기간 선택과 이동 버튼은 반드시 `dates`에 넣고 공통 오른쪽 그룹에서 초기화 바로 앞에 표시한다. 날짜가 없는 목록도 초기화는 오른쪽 끝에 둔다. 검색 조건이 있는 모든 목록은 실제 `onReset`을 제공하며 검색어·필터·날짜·페이지를 해당 화면 기본값으로 복원한다. 필수 업무 대상·저장된 통화 설정·편집 초안을 초기화하거나 저장 API를 호출하지 않는다. 보조 작업(`actions`)은 오른쪽 그룹 앞에, 등록·저장 등 페이지 자체 작업은 기존 페이지 제목 영역에 둔다. 검색 문구·조건·초기화 기본값·API/페이지 처리·권한은 각 화면이 소유한다.

크기는 `ui.search`를 사용한다. 검색어는 기본 400px, 일반 선택 조건은 144px, 항목 사이 간격과 카드 본문 여백은 각각 8px·16px다. 좁은 화면은 검색·필터를 먼저 줄바꿈하고 날짜·초기화 그룹은 마지막 줄에서도 오른쪽 정렬한다. 날짜 구간은 공통 날짜 컴포넌트의 140px 입력과 화살표/M+/M− 묶음을 유지한다. 화면별 검색 입력 너비·compact 제목 숨김·임의 정렬을 추가하지 않는다. 검색어가 없는 화면에 가짜 입력을 넣거나, 전문 편집기·주소록·문서·대시보드 내부 도구를 일반 검색 카드로 강제하지 않는다.

일반 선택창은 `LookupSearchDialog`와 `ui.dialog`의 공통 너비 800px·높이 640px를 사용한다. 결과가 적거나 없어도 같은 기본 크기를 유지하고 목록/본문 안에서 스크롤한다. 좌우 상세 패널이 있으면 공통 너비 1120px를 사용한다. 모바일과 작업 영역이 작을 때는 화면 여백·최대 크기 안으로 축소한다. 문서·넓은 표 등 명시적 `maxWidth`가 필요한 창의 계약과 일반 폼·확인창의 별도 역할은 유지한다.

등록·편집 모달에서 명시적으로 저장하는 폼은 하단 오른쪽에 취소와 저장을 이 순서로 배치한다. 취소는 보조 버튼, 저장은 공통 `SaveButton`을 사용한다. 본문과 작업 영역에 여백을 두고 좁은 화면에서는 입력란을 세로로 배치한다.

대시보드 알림 행의 호버·키보드 포커스 배경은 `dashboardItemSx`의 행 전체에서 관리한다. 본문만 별도 호버색을 칠하거나 우측 확인 영역을 흰색으로 남기지 않는다. 텍스트 확인 버튼은 투명 배경으로 같은 행 배경을 보이고, 원본 열기와 개인 확인의 별도 콜백·비활성 상태는 유지한다.

## 전역 키보드 계약

Esc 닫기는 `AppDialog`와 업무 임시 Drawer의 `WorkspaceDialogRoot`가 같은 `useModalDismiss` 계약을 사용한다. 일반 MUI 키 처리를 우선하고, 포커스가 상단 메뉴/탭 등 모달 밖에 있을 때만 document의 미처리 Esc를 가장 위의 실제 표시 모달에 전달한다. 숨긴 업무 탭·닫힌 모달은 제외하며 드롭다운/메뉴·달력·인라인 패널의 자체 Esc, IME 조합·수정 키·키 반복을 가로채지 않는다. 기존 `onClose(event, 'escapeKeyDown')`·미저장 확인·저장/결과 불명 잠금·`disableEscapeKeyDown`을 유지하고 비동기 닫기 확인 대기 중 중복 요청은 차단한다. Esc로 저장/선택/문서 취소를 실행하거나 DOM에서 모달을 강제 제거하지 않는다. 개별 화면에 document Esc 리스너를 추가하지 않는다.

앱 안의 미저장 변경 확인은 `PageDialogProvider`의 `purpose: 'discard'` 공통 모달로 통일한다. 버튼은 계속 작성 / 변경 사항 버리기이며 기본 포커스는 계속 작성에 둔다. 메뉴 교체·탭 닫기/전체 닫기·원본 창 닫기/다시 불러오기는 비동기 확인 응답을 기다린 뒤 실행한다. 취소·Escape·배경 닫기는 입력과 탭을 보존한다. 브라우저 새로고침·종료의 `beforeunload` 보호는 브라우저가 제공하는 경고를 유지하며 앱 모달로 대체하거나 비활성화하지 않는다.

전체 초안 폐기를 승인한 앱의 명시적 다시 불러오기는 짧은 일회성 승인 구간으로 중복 `beforeunload` 경고만 건너뛴다. 이후의 직접 브라우저 이동·새로고침·종료 보호는 다시 적용한다. 확인 모달을 거쳐 Delete로 탭을 닫았을 때도 모달 포커스가 해제된 뒤 남은 탭으로 포커스를 복귀한다.

업무 탭은 제목 → 고정 24px 상태 영역 → 20px 닫기 동작 순서로 중앙 정렬한다. 미저장은 글리프 대신 6px 원으로 표시하며 로딩 중에도 유지한다. 별도 14px 영역에는 로딩 표시를 우선하고 로딩이 끝나면 대기 중인 외부 변경 아이콘을 표시한다. 상태가 없어도 영역 너비를 유지하고 닫기 버튼에 음수 여백을 사용하지 않는다. 긴 제목만 말줄임하며 전체 제목·상태 설명은 접근 가능한 이름과 툴팁으로 보존한다.

우클릭 메뉴를 가진 DOM 항목은 `tabIndex={0}`과 `data-keyboard-context-menu`를 선언한다. 공통 처리에서 Shift+F10 또는 ContextMenu 키로 같은 메뉴를 열고, 메뉴의 방향키/Enter/Esc와 원래 항목으로 복귀는 MUI 메뉴 동작을 유지한다. 입력창·자식 버튼의 키를 부모 행 메뉴가 가로채지 않는다. 업무 탭은 Delete로 닫을 수 있으며 기존 미저장 확인을 그대로 거친다. 닫힌 탭 다음(없으면 이전) 탭으로 포커스를 복귀하고 다른 곳으로 이동한 포커스를 빼앗지 않는다. 탭 내부 닫기 아이콘 대신 Delete를 사용하므로 Tab은 탭 그룹에서 다음 독립 컨트롤로 이동한다.

배정 카드에서 Enter는 기존 선택/메뉴, Space는 드래그 시작이다. 방향키는 대상 탐색, Home/End는 첫/마지막 대상, Space/Enter는 놓기, Esc/Tab은 드래그 취소다. `data-keyboard-drag`는 드래그 중 공통 입력 이동이 센서의 키를 가로채지 않게 한다. 키보드 대상으로 선택한 실제 droppable ID는 드래그별 ref에 보존해 스크롤/렌더링/연속 키 입력으로 다른 곳에 놓이지 않게 한다. 대상이 사라지면 다른 대상으로 대체하지 않는다. 마우스는 기존 pointerWithin 규칙을 유지한다. 동일한 기존 배정 콜백·권한·완료/실적 잠금·명시적 저장을 사용하고 키보드 입력 자체로 운영 자료를 저장하지 않는다. 잠긴 카드도 상세/허용 메뉴는 키보드로 접근할 수 있다.

숨긴 파일 input은 실제 button의 click 콜백으로 열어 Enter/Space의 사용자 활성화를 유지한다. label 안의 component="span" 버튼처럼 콜백 없는 가짜 버튼을 쓰지 않는다. `test:keyboard-actions`는 실제 카드/메뉴/파일 선택의 한영베 PC·모바일 조합과 업무 탭 닫기, 키보드 대상 안정성 검사를 수행한다. 이동/설정의 드래그 대안은 native 버튼 또는 명시적 키보드 센서여야 한다. 대시보드 방향키 재정렬과 관리 대상 목록의 클릭/Enter/Space 이동은 해당 드래그의 동등한 대안이다.

전체 화면 감사는 `npm run test:keyboard-audit`로 페이지/공통 컴포넌트의 JSX를 검사한다. 단일 선택 그룹의 공통 표식, 양수 tabindex, 클릭/더블클릭 전용 행·카드의 키보드 진입 누락과 직접 Enter/Tab 처리의 정책 우회를 확인한다. 자식 Radio/Button·DnD가 조작을 소유하는 경우는 별도 분류한다. `npm run test:keyboard-domains`는 물류·봉제·회계·인사·급여의 대표 로컬 화면 회귀를 순차 실행하며, 특정 묶음은 이름 인자로 재실행한다. 소스 감사 통과와 운영의 모든 상태를 수동 검수한 것은 구별한다.

네이티브 버튼이 아닌 클릭 가능한 행/카드는 `activateOnKeyboard`를 사용하고 DOM 순서에 `tabIndex={0}`으로 참여한다. 더블클릭으로 열던 항목은 같은 업무 콜백을 전달한다. 자식 버튼의 이벤트로 부모 행이 열리지 않게 target/currentTarget을 구분하며 숨김·읽기 전용/비활성 업무 상태는 포커스 진입을 제한한다. 새 원자료 등록을 Tab이나 Shift+Tab으로 실행하지 않는다. 기존 값의 유일한 정확 일치 확정 규칙과 일반 입력 이동을 구분한다. 문서 입력과 일반 폼의 Enter 처리는 동일한 `textInputKeyDown`을 호출하고 날짜/시간·달력·여러줄 편집을 가로채지 않는다.

기준은 [WAI-ARIA APG 키보드 인터페이스](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)와 각 위젯의 [버튼](https://www.w3.org/WAI/ARIA/apg/patterns/button/), [콤보박스](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), [체크박스](https://www.w3.org/WAI/ARIA/apg/patterns/checkbox/), [모달](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) 패턴이다. 모든 컨트롤에 같은 키 동작을 덮어씌우지 않고 의미에 따라 공통 처리한다.

이전 사용자 지시로 유지하는 BARO 편의 규칙은 표준 기본 동작과 구별한다. **닫힌 코드/이름 입력의 Enter/Tab/blur는 유일한 정확 일치만 확정**하며 부분/중복/미일치는 Enter/Tab으로 선택창을 연다. Shift+Tab은 검색을 열지 않는다. **열린 검색창에서 Tab은 강조 후보를 확정하지 않는다.** 선택 후 다음 입력 이동도 BARO 규칙이며 다중 선택은 최종 확인 후에만 이동한다. 방향키로 선택 상태도 바뀌는 네이티브 라디오와, 확정 전 탐색만 하는 세그먼트 버튼을 혼동하지 않는다.

키 해석은 `utils/keyboardPolicy.mjs`, 경계·초기 포커스·다음 입력 이동은 `utils/formFocus.mjs`, 코드 매칭은 `utils/expenseLookup.mjs`, 검색 선택은 `LookupInput`/`LookupSearchDialog`/`SearchableSelect`가 담당한다. 네이티브 버튼의 Enter/Space와 체크박스의 Space를 상위 검색 핸들러가 중복 처리하지 않는다. 다중 검색 모달 안의 체크박스 Enter만 공통 전체 확정으로 처리하며 일반 체크박스의 동작은 유지한다. IME 조합 중 Enter와 keyCode 229, 수정키 조합, 이미 처리된 이벤트는 공통 명령으로 실행하지 않는다.

검색 결과 행을 마우스로 누르면 실제 행 포커스와 강조 후보를 일치시킨다. 단일 클릭은 탐색이고 Enter·선택 버튼·더블클릭이 확정이다. 행에서 방향키로 탐색하면 실제 포커스도 새 행으로 이동하며 검색 입력에서 탐색할 때는 입력 포커스를 유지한다. 선택 행과 우측 고정 작업 셀은 공통 선택 배경을 사용하고 마우스가 벗어나도 선택 상태의 배경을 유지한다.

페이지는 DOM 순서로 입력 순서를 배치하고 필요한 경우 `data-initial-focus`만 선언한다. 양수 tabindex로 순서를 맞추거나 화면별 타이머/전역 검색으로 포커스를 빼앗지 않는다. 도메인 전용 단축키/특수 편집기는 명시적 경계와 실제 업무 콜백을 유지한다. 읽기 전용·숨김·비활성은 입력 순서에서 제외하며 모달은 내부에서 순환하고, 닫기는 미저장 확인·저장 중 제한을 따른다. 공통 회귀 검사는 `npm run test:keyboard-navigation`이다. 기존 화면 전체의 도메인 단축키 전환 완료를 의미하지 않는다.

세그먼트 버튼은 공통 `MuiToggleButton.defaultProps.disableFocusRipple`로 짙은 포커스 ripple을 끈다. 현재 포커스는 파란 테두리로 표시하며 선택 배경과 클릭 피드백은 유지한다.

단일 선택 세그먼트는 `data-focus-next="group"`와 공통 `formFocus.mjs`를 사용한다. Tab/Shift+Tab은 그룹당 한 번만 멈추며 다시 진입하면 선택 항목(없으면 첫 활성 항목)에 포커스를 준다. 방향키/Home/End는 활성 옵션 사이의 포커스만 이동하고 Enter/Space/클릭으로 확정 후 다음 입력으로 이동한다. 탐색만으로 값을 변경하지 않는다. 포커스는 선택 배경과 별개의 공통 파란 테두리로 표시하며 초기 프로그램 포커스에도 적용한다. 화면별 방향키 처리나 tabindex 상태를 중복 구현하지 않는다. 다중 선택 그룹에는 이 단일 선택 표식을 붙이지 않는다.

페이지·모달·임시 Drawer의 초기 포커스와 입력 순서는 `formFocus.mjs`의 공통 처리를 사용한다. 첫 편집 항목을 우선하되 검색이 있는 `ListDetailDialog`는 `data-initial-focus-search`로 검색칸을 우선한다. 목록 유무와 관계없이 검색칸에서 시작하며 로딩 중 검색 비활성화를 이유로 오른쪽 편집칸으로 이동하지 않고 검색 활성화를 기다린다. 이후 사용자가 옮긴 포커스는 재조회로 빼앗지 않는다. Tab/Shift+Tab은 숨김·비활성·읽기 전용을 건너뛴다. 단일 선택을 확정하면 다음 항목으로 이동하며, 다중 선택은 최종 확인 때 이동한다. 검색 취소는 원래 입력으로 복귀한다. 일반 입력의 Enter 이동과 여러줄 개행·IME·날짜 구간 편집을 구분한다. 별도 타이머나 전역 `document.querySelectorAll`로 포커스를 옮기는 화면별 예외를 추가하지 않는다. 단일 ToggleButtonGroup에는 `data-focus-next="group"`, 특수 편집기에는 `data-keyboard-navigation="off"`, 명시적 첫 항목에는 `data-initial-focus`를 사용한다. 업무 탭/초안과 중첩 모달 복귀를 유지한다.

일반 조회 표는 `tableLayout.js`의 공통 규칙으로 PC 작업 영역에 먼저 맞춘다. 불필요한 최소 너비·고정 열 너비를 풀고 가로 여백과 텍스트 줄바꿈으로 조정하며, 글자나 금액을 축소·생략하지 않는다. 마지막 작업 열의 직접 버튼·버튼 그룹·`DeleteActionButton`은 스크롤 중에도 우측에 남는다. 별도 작업 셀은 `data-table-actions`로 표시한다.

일반 조회 표의 단일 텍스트 셀은 가용 너비를 넘을 때 한 줄 말줄임(…)을 기본으로 사용한다. 창 너비나 확대 비율이 달라지면 CSS가 실제 열 너비에 맞춰 전체 문구를 복원한다. 말줄인 셀에 마우스를 올리면 전체 문구를 기본 툴팁으로 표시한다. 표 밖의 한 줄 텍스트나 복합 셀 안의 이름에도 `data-truncate-text`를 사용할 수 있다. 금액과 수치 셀은 우측 정렬을 사용해 전부 표시한다. 입력 표, wide/document/fixed 표, 작업 열과 복합 셀은 기존 배치를 사용한다. 의도적으로 여러 줄을 쓰는 표나 셀에는 `data-table-wrap`을 지정한다. 말줄임은 화면 표시만 바꾸며 문서 출력·검색·복사에서 원문을 유지한다.

운송 당사자(SHPR/CNEE/NOTIFY) 선택 목록은 고정 비율 표에서도 업체명·주소에 `data-truncate-text`를 적용해 한 줄 말줄임으로 표시한다. 출처 보조 행은 유지하고 전체 원문은 title과 오른쪽 상세에 보존한다.

우측 고정 작업 열의 왼쪽에 구분용 세로선이나 그림자를 표시하지 않는다. 고정 위치·배경·행 호버와 삭제 보호 조건은 유지한다.

스크롤 고정 머리글은 본문 작업 버튼보다 위에 표시하며, 우측 고정 열과 교차하는 머리글은 다른 머리글보다 위에 둔다. 공통 검색창의 ‘선택’ 제목도 상하·좌우 스크롤 중 가려지지 않아야 한다. 표의 작업 열 판별 CSS에는 중첩 `:has()`를 사용하지 않는다.

다단 헤더에서 작업 열은 첫 헤더 행의 마지막 칸을 기준으로 고정한다. 하위 사이즈·기간 행의 마지막 칸까지 작업 열로 처리하지 않는다. 주문 고정 헤더도 공통 header 배경 토큰을 사용해 작업 열과 나머지 헤더의 배경을 맞춘다.

모달과 임시 Drawer에는 닫기 용도의 취소 버튼을 두지 않는다. 바깥 클릭과 Esc는 기존 onClose 및 미저장 확인을 사용하고 저장 중·결과 미확인 상태의 닫기 제한은 유지한다. 저장·확인·선택과 휴가/출고/실적 등록 자체를 취소하는 업무 동작은 구별한다. 취소만 있던 빈 DialogActions는 제거한다.

업무상 열 너비가 필요한 날짜·사이즈·급여 매트릭스는 `data-table-layout="wide"`, 인쇄 문서는 `document`로 명시한다. 고정 비율 요약표는 `fixed`, 유연한 표 안에서 열 설정을 유지하려면 `columns`를 사용한다. 편집 입력이 있는 표는 기존 입력 너비를 유지하고, 공간이 부족하면 표 내부에서 스크롤한다.

- 일반 색상·모서리·표 간격: `ui.js`
- 라벨의 배경·글자·테두리 색상: `labelPalette.js`
- 표·입력창·버튼·Chip의 기본 표시: `index.js`의 MUI 테마
- 화면 배치와 조회 도구: `AppPageContainer`, `PageToolbar`

본문·표·일반 컨트롤의 기본 글자 크기는 13px이며 `ui.typography`, `ui.table`, `ui.control`이 같은 기준을 공유한다. 제목·합계·보조 설명은 각각 별도 의미 토큰을 사용한다. HTML 화면도 `--ui-body-font-size`, `--ui-control-font-size`, `--ui-table-font-size`를 사용한다. CSS 초기화 선택자의 우선순위는 낮춰 MUI나 역할별 토큰을 덮어쓰지 않는다.

페이지별 배치·강조·밀도 조정은 허용한다. 공통 역할의 기본 디자인은 테마/컴포넌트에 먼저 정의하고, 화면에서 필요한 차이만 조정한다. 직접 지정한 값이 있다는 이유만으로 모두 제거하지 않는다.

모달 제목·본문·하단 버튼 영역의 기본 여백은 `ui.dialog`와 전역 `MuiDialogTitle/Content/Actions`에서 관리한다. 저장 동작은 `SaveButton`을 재사용하며 기본 모서리는 일반 버튼과 같다. 화면별 열 구성·넓이·스크롤·특수 작업은 호출부에서 조정할 수 있다.

아이콘형 행 삭제는 `DeleteActionButton`을 사용한다. 활성 상태는 빨강, 비활성은 회색, 호버는 옅은 빨강 배경으로 표시한다. 화면의 삭제 조건·확인창·이벤트 전파는 호출부에서 유지하며 `disabled`, `title`, `aria-label`, `stopPropagation`을 전달한다. 텍스트가 있는 문서 전체 삭제 버튼과 대화상자 닫기 버튼은 별도 역할을 유지한다.

아이콘형 행 추가는 `AddActionButton`의 파란색 `+`를 사용한다. `DeleteActionButton`과 같은 공통 아이콘 크기·상태·접근성 규약을 사용하며 화면별 아이콘·색·패딩을 복제하지 않는다. 추가 위치·행 수 제한·잠금·이벤트 전파는 호출부에서 유지한다. 비용·지급 회차·청구 항목·입출금·작업 기록의 행 추가는 이 컴포넌트를 재사용한다. 새 문서 생성과 추가 항목 메뉴는 행 추가와 구별한다.

일반 컨트롤은 `ui.control`을 단일 크기 기준으로 사용한다. 텍스트·숫자·검색 선택·드롭다운·날짜·월 입력과 버튼은 기본 높이 36px, 글자 13px, 줄 높이 20px다. 아이콘 버튼은 작은 크기 28px·기본 36px·큰 크기 40px를 사용한다. M+/M−는 각 17px와 간격 2px로 전체 36px를 맞춘다. 여러 줄 입력과 복수 선택은 최소 높이에서 내용에 따라 늘어난다. 화면별 높이·폰트 강제 지정 대신 공통 토큰과 테마를 수정한다. HTML 컨트롤도 전역 `--ui-control-*` 변수를 재사용한다.

라벨 색상은 페이지에 HEX로 복사하지 않는다. 기존 `<Chip color="success" />`도 전역 파스텔 톤을 적용받는다. `outlined`는 동일한 배경에 옅은 테두리를 추가한다. 클릭·삭제·비활성 동작은 MUI Chip을 그대로 사용한다.

공통 검색 선택 `LookupInput`의 라벨은 빈 값·비활성 상태에서도 상단에 고정한다. 돋보기는 줄어들지 않는 별도 끝 영역과 공통 작은 아이콘 크기를 사용하고 입력 글자만 남은 너비를 쓴다. 돋보기 공간에 입력 안쪽 여백을 중복 적용하거나 라벨을 겹쳐 놓지 않는다. 모든 일반 복수 선택의 선택 칩은 `LookupInput`의 공통 입력 슬롯 안에 표시한다. SearchableSelect·ExpenseLookupField가 선택값/삭제 콜백만 전달하며 입력 아래 별도 칩 목록이나 화면별 안/밖 선택 옵션을 만들지 않는다. 칩과 검색 텍스트는 같은 테두리 안에서 줄바꿈하고 높이를 늘리며, 돋보기 영역은 따로 확보한다. 긴 이름의 전체 title·삭제/잠금·비활성 기존 선택·직접 검색·IME·Space/Enter/포커스 규약을 유지한다. 화면별 절대 위치나 임시 여백으로 돋보기 겹침을 보정하지 않는다.

회계 입력은 대상 → 회계 코드/내역 → 금액 → 지급 조건/증빙 → 행 작업 순서로 배치한다. 청구 대상·지급 대상은 코드와 읽기 전용 이름, 검색 목록과 우측 상세의 공통 구성을 쓴다. 입출금의 회사 계좌는 각 행 From/To에 포함하며 별도 상단 선택과 중복시키지 않는다. 날짜·통화·문서 유형 등 공통 조건과 주문 청구의 원본 산출 조건은 문서 헤더에 둘 수 있다.

공통 검색 선택은 Enter/Tab에서 코드·전체 이름이 정확히 일치하는 유일한 항목만 바로 확정한다. 부분 입력은 후보가 하나뿐이어도 입력한 검색어를 유지한 모달을 열어 직접 선택한다. 화면별로 유일한 부분 일치를 자동 확정하는 예외를 추가하지 않는다. blur 정확 일치·IME·Shift+Tab·선택 후 포커스 복귀는 유지한다.

운송 SHPR/CNEE/NOTIFY와 특송 일반 의뢰인도 `ShippingLookupInput` → `LookupInput`을 사용한다. 클릭/포커스만으로 관리창을 열거나 읽기 전용 돋보기 입력으로 대체하지 않는다. 회사·고객 범위의 원본 조회가 완료된 후보만 정확 일치로 확정하며, 조회 중/실패/중복/부분 입력은 검색어를 유지한 기존 목록·상세 관리창에서 확인한다. 원본 저장과 운송건 적용은 별개다.

새 상태 표시는 공통 컴포넌트를 사용한다.
완료·경고·오류·입력 검증 알림은 `AppNotice`와 `AppContext.showNotification`을 통해 상단 중앙 토스트로 표시한다. MUI `Alert` 직접 사용은 토스트 렌더러인 `NotificationToast`에만 둔다. 완료/정보는 3초, 일반 경고/오류는 6초이며 재시도·설정 이동 등 작업이 있으면 직접 처리/닫기까지 유지한다. 동시 알림은 대기열로 전달하고 동일 메시지는 합치며 비활성 탭의 알림과 오래된 작업 버튼은 제거한다. 모달 위에서도 표시하며 입력값·포커스를 변경하지 않는다.
`PageSectionHeader`는 제목·작업만 표시한다. 반복적인 이름·코드 입력 안내와 설명 부제목은 표시하지 않는다. `MuiFormHelperText`의 공통 `FieldFeedback`은 일반 안내를 생략하고 실제 입력 오류를 토스트로 보낸다. 금액·수량·문서 내용·업무 상태·확인/선택 대화상자는 설명과 구별해 보존한다. 띄어쓰기는 저장 자료를 렌더링할 때 임의로 바꾸지 않고 화면 문구 소스에서 교정한다. `npm run check:ui-notices`로 직접 Alert 사용·브라우저 alert·문구 회귀를 검사한다.

필수 입력이라는 일반 안내를 창 진입 시 오류 토스트로 띄우지 않는다. 저장 검증이 실패하면 실제 오류 칸을 `error`로 강조하고 첫 오류 칸에 포커스·스크롤을 제공한다. 폼 전체 검증을 한 번 알리는 화면은 같은 오류를 각 칸의 `FieldFeedback`으로 다시 전송하지 않는다. 입력을 고치면 해당 칸의 강조를 해제하며 새 폼/다른 직원으로 열 때 이전 검증 상태를 초기화한다. 직원 등록·수정은 이 기준으로 이메일의 역할별 필수 여부·이름·공장·날짜 오류를 표시한다.
반응형 모바일 메뉴 Drawer는 PC 구간에서 실제로 닫힌 상태여야 한다. CSS로만 숨긴 열린 모달이 본문을 접근성 트리에서 제외하거나 포커스를 막지 않게 한다.

회계 목록의 여러 코드는 첫 코드와 `외 N건`으로 요약하며 항목 수는 중복 코드의 별도 행도 포함한다. 비용 수정은 지급 방식/회차와 증빙·참조를 모달로 옮겨 한 줄을 유지한다. 축약한 단위·내역은 title로 전체 내용을 제공한다. 명명된 회사 계좌의 확정 값은 계좌명만 표시하고 선택창에서는 계좌번호·통화로 구분한다. 입출금의 연결 비용은 코드·금액별 행으로 표시하되 실제 은행 거래를 중복 집계하지 않는다.

```jsx
<StatusLabel label={translatedLabel} tone="blue" />
<StatusLabel label={translatedLabel} tone="green" dot />
```

| 의미 | tone | MUI color |
| --- | --- | --- |
| 진행·정보 | blue | primary / info |
| 정상·완료 | green | success |
| 주의·검토 | yellow | warning |
| 오류·지연 | red | error |
| 중립·준비 | gray | default |
| 별도 분류 | purple | secondary |

기존 급여 유형 등의 분류에는 `orange` 등 기존 명명 팔레트를 유지한다. 상태 키와 톤의 연결은 해당 도메인에서 명시한다. 번역 문구나 진행률로 상태를 추측하지 않는다. 점은 색상을 보완하는 장식이며 상태 문구를 함께 표시한다.

MUI가 아닌 배경·막대에도 `LABEL_PALETTE` 또는 `getLabelPalette()`를 재사용한다. 출력 문서의 불변 스냅샷과 인쇄 전용 색상은 별도 계약을 따른다.

비용 신청처럼 HTML/CSS로 작성된 화면은 `CssBaseline`이 내보내는 `--color-*`, `--ui-*`, `--label-{tone}-{background|text|border}` 변수를 사용한다. 브라우저 검증도 실제 앱처럼 공통 ThemeProvider와 CssBaseline을 포함해야 한다. 표의 열·필터·선택·조회 정책은 유지하며, 비용 내역의 구분을 결재 상태로 바꾸어 표시하지 않는다.
